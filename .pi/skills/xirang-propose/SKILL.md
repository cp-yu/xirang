Propose a new change or update an existing change by organizing the actual draft with the user. Reuse the confirmed design, discuss ideas and gaps discovered while writing, and complete the Semantic Delta and Change Plan for implementation. Explore maintains the intermediate design and feasibility evidence; Propose writes and reviews the complete Change without inventing material decisions.

## Readiness boundary

Before creating or updating Change artifacts, check whether any unresolved decision affects this target. If one remains, complete the necessary read-only discovery and permitted record maintenance, then present the decision and stop. Do not draft the settled portions first: a partial Change does not make the whole target ready. Authorization to investigate or prepare is not an explicit override of this boundary. If the user explicitly authorizes drafting despite the blocker, stay within that authorization and leave dependent target semantics unwritten until decided; never turn an undecided outcome into accepted content.

**Xirang Philosophy**

1. Xirang is a structured representation of human intent that an Agent can compile.
2. One Xirang Semantic Model is persisted as a single whole in the four partitions `metamodel/`, `elements/`, `relationships/`, and `views/`; a Semantic Delta uses the same four partitions and adds `operation`.
3. A change reconciles a Semantic Delta toward the target steady state. `proposal.md`, `design.md`, and `tasks.md` are compilation scaffolding, not competing sources of truth.
4. The Xirang Semantic Model is complete only when an Agent need not guess decisions that affect element hierarchy, contracts, or relationships.
5. The Agent acts like a compiler and faithfully translates authorized human intent. Existing code is current implementation evidence and MUST NOT silently override the Xirang Semantic Model.

**Business Specification Standard (4+N)**

For business-specification Elements, prepare scope/non-goals, the complete business mechanism, exceptions, and key acceptance outcomes; add Sections only for independently maintained commitments. Before exploring such a Contract or authoring/revising its Kind or Contract, read `.xirang/references/xirang-business-specification-standard.md` for applicability, canonical structure and self-checks. Generic framework or organizational Elements do not trigger this format.

**Test Quality Guidance**

Persistent tests protect observable behavior and provide fast, trustworthy feedback.

1. Repeatable in isolation. A test creates and cleans up its own state, does not depend on execution order, shared mutable state, or external mutable sources, and is fast enough for its intended feedback loop.
2. Coupled to behavior, decoupled from structure. A plausible behavioral mutation, such as changing a boundary comparison or deleting a required state update, must make the test fail. Refactoring, implementation replacement, prose changes, formatting changes, or semantic model prose changes must not fail the test when behavior is preserved.
3. One clear failure reason. A failing test identifies one broken behavior. Do not split one behavior merely to mirror multiple specification sentences, and do not combine unrelated behaviors in one test.

Design for testability: when behavior is difficult to test because of hidden global state, mixed responsibilities, or inaccessible results, improve the interface before writing the test. Do not compensate with internal mocks or implementation-coupled assertions.

Before adding a persistent test: inspect existing tests and prefer extending or replacing an existing test that already owns the behavior; choose the cheapest test boundary that can detect the intended defect; one test may cover multiple Acceptance Cases when they describe the same behavior and failure reason; add a boundary case only when it can expose a distinct plausible defect; keep slower integration or end-to-end tests only for cross-boundary behavior a cheaper test cannot prove; use one-time verification for build, typecheck, migration inspection, and other evidence that does not justify a maintained test; update or delete tests whose behavior changed, disappeared, became duplicated, or became coupled to obsolete structure.

**Xirang Semantic Model Context**
- Resolve the absolute Project Root. The Semantic Model is stored in `.xirang/model/{metamodel,elements,relationships,views}/`; use the CLI projections below to load needed context, not a recursive read of all partitions. Locate the unique Project Root Element (`parent: null`) through outline and query its Declaration.
- Use `identity` as the only way to reference a semantic object. FQN, syntax position, and derived local names are generation artifacts and never appear in a persistent source.
- Read relevant parent and children as abstraction/refinement context. Do not assume a fixed element-kind hierarchy or treat nesting as ownership.
- An Element Contract is the body of its Element unit: one Element has at most one Contract, expressed as `## Specification`, and whether a Contract is required comes from the `contract` field of its Element Kind.
- Use `xirang arch outline --format json` as the navigation projection: it returns the complete Element hierarchy without Definitions, Relationships, or Metamodel unless explicitly selected.
- Use `xirang arch impact <identity> --depth <n> --json` for identity-only refinement context and a relationship summary. Use `--paths` only when relationship paths are needed; impact never returns Element Definitions or Contracts.
- Use `xirang arch query <identity> --json` for the complete Declaration of a selected identity; add `--contract` only when that Element Contract is needed. Batch only the selected identities whose semantics answer the current question.
- Before expanding a read or issuing a batch, state the concrete question it must answer and include only the identities or file ranges required for that question. Start discovery with `xirang arch search <query> --limit <n>`.
- For code evidence, locate symbols or definitions first with LSP or `rg`, then read the smallest relevant implementation range. For tests, locate the test that owns the behavior before opening test files; do not read whole directories by default.
- Use concurrency only for bounded, independent reads. Do not emit or retain raw nested JSON when a concise projection or selected fields answer the question.
- If a tool truncates output, treat it as incomplete: narrow the query or split it into bounded reads, then retrieve and verify the missing portion before relying on the result.
- If specific semantic context is missing, query that identity rather than expanding every identity returned by impact. If global model understanding is lost after context compression, session switch, or a model diagnostic, run `xirang arch snapshot --format json` for the full Declaration/Relationship/Metamodel baseline, then query only required Contracts.
- The Agent MUST NOT guess missing Definition or Contract semantics from identity, title, an old summary, residual conversation context, or implementation evidence.
- Default unit naming is `elements/<identity>.md`, `metamodel/<kind identity>.md`, `views/<view identity>.md`, and `relationships/<relationship kind identity>.yaml` grouped by Relationship Kind; a change reuses these names under `.xirang/changes/<name>/`. Directory and file names carry no model semantics: every entry declares its own `entity` and `identity`, and loading locates entries by those, never by path.
- Treat code paths, symbols, imports, and calls from CodeGraph or ACE/`rg`/`read` as current implementation evidence only; do not promote them to elements or relationships without declared model intent.
- If the model is missing, report `Semantic Model unavailable`. If it is incomplete or unsupported, identify the root, identity, contract, or relationship gap.
- A read-only exploration MAY degrade to available model and code evidence with the limitation disclosed. Workflows that compile or write semantics MUST stop when required model context is missing or incomplete; never treat a missing collection as complete and empty.

**Element Definition Semantics**

- A Definition SHALL state what the Element is, why it is modeled as an independent Element, what it includes, what it excludes, and, where needed, how it differs from its parent, children, and siblings.
- A Definition MUST NOT be a rewrite of the title or a one-sentence "used for ..." summary; it expresses concept identity and scope boundary, not implementation files, symbols, call relationships, or the current approach.
- Responsibilities, guarantees, constraints, behavior, Sections, and acceptance cases belong to the Element Contract; approach and rationale belong to `design.md`; change motivation and migration history belong to `proposal.md`.

**Element Contract Semantics**

- An Element Contract SHALL express completely the responsibilities, guarantees, constraints, and behavior the host Element carries at its own abstraction level; children may further refine or jointly fulfill those commitments. A parent must independently state its complete commitments at that level without requiring readers to read child Contracts. Preserve necessary coverage across abstraction levels without copying child Contracts item by item.
- Scope states this Element's responsibilities and necessary exclusions, not every thing it does not do. Whole-Change goals and non-goals belong in `proposal.md`; implementation choices, rejected approaches, and reasons needed to understand the design belong in `design.md` (execution work belongs in `tasks.md`). For `pi-native-markdown-preview`, “自研 HTTP 预览服务” is an implementation approach exclusion: route it to `design.md`, not the Element Contract's Scope and Non-goals.
- State conditions, behavior, and results directly; remove explanations that add no meaning. For example, “系统 MUST 对提交的来源版本进行严格校验，以确保更新始终基于最新记录，避免过期操作对现有内容造成覆盖。” can be shortened to “来源版本过期时，MUST 拒绝更新，记录保持不变。”
- State each rule once at the same abstraction level. Scope does not repeat the complete pipeline; Business Logic explains the mechanism; exceptions add distinct conditions and outcomes; acceptance uses concrete inputs and results to verify the commitment. Preserve complete commitments across parent/child levels rather than removing them as duplicates.
- Reuse accurate existing wording and change only affected behavior. Do not polish unrelated passages or repackage clear user-confirmed language merely to make it sound formal. Preserve conditions, numbers, exceptions, timing, and concrete examples. Keep implementation internals and process detail out of Contracts, and name Sections for enduring verifiable commitments, not one-time gap, recovery, or migration actions.
- A Section SHALL express one independently evolvable normative commitment under a stable identity. Its boundary is whether that commitment can be added, modified, or removed on its own; do not split mechanically by sentence, clause, `SHALL` count, or target Section count. Content that only restates the Declaration definition or the union of sibling Sections without adding a normative commitment does not form a Section; independent invariants, ordering, atomicity, consistency, or completion conditions are preserved. Business-specification Contracts use the mandatory 4+N groups; related mechanism details remain inside Business Logic instead of becoming separate Sections.
- A Section body is free-form: prose, lists, tables, decision tables, formulas, pseudocode blocks, event triples, or any other carrier that expresses the item completely. Do not force a carrier, require fixed sub-headings, or treat sub-headings as identity. `### Section:` headers are the only structural unit inside `## Specification`.
- `#### Acceptance Case:` is used only inside the key-acceptance-cases Section. It is not a general structural requirement; do not demand Acceptance Cases from other Sections, and do not let Acceptance Case count determine the number of persistent tests.

**Structural Decomposition Guidance**

- Before forming or reorganizing an Element hierarchy, run `xirang config project --json` and read the normalized `decomposition` value from its JSON output. Do not inspect or reinterpret the raw config, and do not substitute another method.
- Read the guidance file at that resolved path in full. When it is missing or unreadable, stop hierarchy formation and ask the user once.
- Decomposition guidance selects the dimension used for hierarchy abstraction and refinement. It does not override authorized user intent, the Xirang Semantic Model, Element Contracts, Relationships, evidence authority, or the current workflow's read/write boundary.
- Keep every same sibling set on one dimension, make it MECE for the confirmed scope, and confirm breadth-first. Do not mix responsibility, lifecycle, deployment, or implementation dimensions within one sibling set.

## Confirmed design inputs

MUST read `.xirang/references/xirang-design-record.md` at entry. It owns record discovery, confirmation authority, reload/selective reads, versioned updates, writing rules, coverage and consumption. Apply those gates at the flow points below; do not duplicate full reads per section. A record is formation evidence, not a complete Delta. Local decisions and record revisions can stay in Propose; practical feasibility experiments or substantial redesign return to Explore.

## Documentation and gap handling

- **Local detail and faithful writing**: organize confirmed mechanisms into prose, diagrams, Acceptance Cases, and task/verification arrangements. Independently handle minor details within the agreed scope and approach, case organization, and expression or derivation errors; preserve the user's clear wording when it is already accurate. Do not use "reasonable elaboration" or delegated discretion over minor details to add substantial design content on your own. Before presenting a draft and after a local revision, compare authored branch outcomes, defaults, error results, and restrictions with the confirmed source: check the triggering condition, action, affected operation or state, time boundary, and result. If the wording requires or forbids an outcome the source leaves open, identify that difference instead of treating it as a paraphrase. Remove unintended strengthening; use Decision gap when completing the target requires a substantive choice. A ruling limited to one local edit does not confirm other draft additions. Disclose permitted minor additions with their basis and locations at completion. Do not ask the user to fix an Agent writing error when the confirmed design already determines the answer.
- **Decision gap**: when completion would change a confirmed commitment, expand scope, or settle a material business or architecture trade-off, explain the gap and alternatives, recommend with reasons, then ask one focused question and wait before writing the choice as settled. Discuss and confirm small content or approach adjustments within Propose and update the shared record under its permission rules; a design discussion or record revision alone does not require changing workflow. Return to Explore when feasibility needs experimental judgment, the direction must be reconsidered, or substantial design must be redone; resume Propose after that work. A direct-Propose request, a request not to ask questions, or a readiness override does not supply a missing decision; report the blocker instead of guessing.
- **Propagation and disclosure**: after confirmation, record the decision through the shared protocol and reconcile the affected Delta and Plan together. Do not hide new observable behavior solely in design or tasks. Reconcile permitted minor observable details into the Contract and Plan and disclose their basis and locations, without labeling them as user confirmations; if retained for later discussion, they remain pending. Track additions in the conversation for the final report; do not create a supplement ledger or add authorship/confirmation status to normative Contract text. Completion disclosure does not replace prior confirmation for material decisions.

## Drafting and user review

For a simple change, write the complete draft, then present its concrete differences and remaining questions together for user review. Resolve any material decision before authoring content that depends on it. For a complex change, organize drafting and review around one mechanism or a group of related Elements; show the actual draft for that group, obtain confirmation, and continue. Do not mechanically ask for approval of each Element or treat the number of Elements as the review plan.

Preserve artifact dependency order while using these review units. Discuss new ideas and questions as they arise; do not optimize for completing one invocation without interaction. After a local revision, recheck the affected mechanism and artifacts. Unresolved decisions affecting the target block completion; artifact completeness and CLI success do not establish semantic readiness.

## Flow

   - If the user explicitly overrides the readiness recommendation, continue within that authorization, but the override does not authorize guessing source decisions.    - For an existing change, assess readiness from existing artifacts, current input, the confirmed Design Summary, formal source, and implementation evidence together.
   - Keep readiness, missing-item, and override state in the conversation only; do not copy it into change artifacts.

   - If the user explicitly requests a new change and the ID already exists, stop and ask for a different ID. Do not overwrite, continue, or synthesize an alternative ID.
   - If the user explicitly requests an existing change, update that change in place without asking for another ID.

Reuse their identities. For each parent carrying an affected commitment, determine its target obligations from the complete confirmed design, including the Design Summary even when the partial record has no separate entry for that parent; do not narrow those obligations to what its current Contract already says. Compare them with the parent's current clauses alone: identify the clause that determines each promised outcome with its required conditions and limits. Child refinement does not remove a commitment assigned to the parent; a generic delegation or a clause merely consistent with the child rules does not establish that the parent states those obligations. If those clauses still permit a ruled-out outcome or leave a confirmed outcome undetermined, include the missing or changed commitment in proposal Behavior Source and the corresponding Section Entries. Preserve the conditions, numbers, exceptions, and timing that determine the parent's promised outcomes; child implementation detail need not be repeated. A no-op needs existing clauses that already carry those commitments, even when the Declaration is unchanged. Review groups control drafting order, not the whole Change's source scope. An optional-contract Element without a Contract does not by itself require a new one.

For every added or modified Declaration, write the complete target Definition, not a summary of what changed. Implementation movement or call/import evidence alone is not a structural change.

A partial record leaves room for unconfirmed structure: when source impact requires a new or reorganized hierarchy, apply the Structural Decomposition Guidance to the unresolved scope and obtain user confirmation before authoring target sibling sets. If the configured guidance is unavailable or insufficient, stop Formation and ask one focused question; do not fall back to another method or infer structure from implementation layout.

Compile the record's confirmed `structure` objects into matching Declaration, Relationship, or Kind entries (never re-derive kind or parent from implementation relationships), or confirm no-op when the formal model already matches. Resolve target-affecting pending questions with the user; retain reasons for entries outside this target. Excluded and informative material goes to Plan or provenance without inventing obligations. Author only canonical `### Section: <title>` headings; a Section body is free-form. Rely on combined change validation for deterministic header compatibility. Follow the returned Specs authoring contract.
   - Route obsolete-test rationale from **Test Maintenance** to `design.md` and concrete test updates/removals to `tasks.md`. Route **One-time Verification** items to goal verification directions as evidence-only checks with no persistent test file; absence assertions reference the removed Section.

If an Element's concept identity, independent modeling reason, scope, or hierarchy boundary remains unresolved, stop and ask one focused question instead of guessing the Definition. Handle only minor details autonomously and discuss substantive additions before settling them. Complete the applicable whole-draft or mechanism-group review before the closing gate.

Writing a choice in Design does not itself confirm it.

Do not include implementation files, test actions, test layers, commands, or nested Checks; Apply chooses these from current code and test evidence. Include only user-confirmed target ordering; ordinary technical dependencies belong to Apply.

For each target behavior needing implementation, state the behavior, relevant boundary, and expected observable result without fixing a specific test, command, file, or test decomposition. Keep implementation and testing arrangements in Apply rather than duplicating them in tasks.

A valid reference or matching topic does not establish agreement; compare what each statement requires, forbids or leaves open. Correct source-determined writing errors yourself; when a substantive decision is needed, present all findings and request one user ruling at a time. Agreement among artifacts cannot excuse a shared omission.

## Artifact Contract

**Document Language Contract**:
- Follow the returned `configProjection.prompt` for prose language and canonical-token boundaries; do not reinterpret raw config.
- Keep the template structure unchanged. If no `proseLanguage` projection is present, keep the default writing behavior for prose.

Tasks use a single goal-level checklist. Each goal states the intended outcome, references its target Contract Section, and identifies behavior, relevant boundary, and observable verification direction. Apply determines files, tests, commands, and technical ordering from repository evidence. Only explicit user-required ordering is encoded in goal order.
